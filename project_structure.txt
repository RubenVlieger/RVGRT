# RVGRT (RubenVlieger GPU Ray Tracer) - Exhaustive Project Architecture & LLM Context

This document is the master architectural blueprint for RVGRT, an advanced, cross-platform (Metal/CUDA) Minecraft-like path-traced voxel engine. It is specifically designed to provide LLMs with maximum context, accelerating debugging, feature implementation, and optimization.

## Recent Restructuring (March 2025)

The codebase was recently reorganized to improve maintainability and provide clearer separation of platform-specific code:

### New Directory Structure

**Platform-specific code** has been moved to dedicated subdirectories:
- `src/renderer/Metal/` and `include/renderer/Metal/` - Metal implementations (macOS)
- `src/renderer/CUDA/` and `include/renderer/CUDA/` - CUDA implementations (Windows)
- `src/renderer/D3D12/` and `include/renderer/D3D12/` - DirectX 12 implementations (Windows)

## 1. Executive Summary & Philosophy
- **Core Goal:** Real-time path tracing of massive voxel terrains at high framerates using GPU compute.
- **Rendering Paradigm:** A deferred, multi-pass compute pipeline. It eschews traditional rasterization in favor of pure compute raytracing.
- **Platform Strategy:** C++ core logic, abstracted `Renderer` interfaces, and OS-specific backends. Currently, **Apple Metal (macOS)** is the primary, actively developed path using Objective-C++ (`.mm`) and `.metal` shaders. A CUDA/D3D12 fallback exists on Windows but is not actively maintained.
- **Memory Philosophy:** GPUs have limited memory; a massive world cannot fit in dense grids. The engine dictates a strict, aggressive **3-Level Sparse Voxel Octree (SVO-like)** structure mapping world space to toroidal fixed-capacity GPU buffers.

## 3. Data Structures & Memory Management (The Voxel Backbone)
To render millions of voxels smoothly, the world is broken down into a 3-level hierarchical sparsity model managed by `MaterialMap` and `BrickPool`.

### Levels of Abstraction
1. **Level 1 (Indirection):** A toroidal 3D `MTLTexture` (`_indirectionTexture`, R32Uint). It wraps around the camera's spawn. It holds a single integer index pointing to the `SectorBuffer`. If a sector is unallocated, it reads `SECTOR_HANDLE_EMPTY`.
2. **Level 2 (Sector Buffer):** A flat buffer of `SectorInfo` structs. A "Sector" represents a 32x32x32 span of voxels space. `SectorInfo` contains a 64-bit `brickMask` denoting which inner 8x8x8 bricks actually exist, and a `baseBrickIndex` pointing into the `BrickPool`.
3. **Level 3 (Occupancy Buffer / Sub-Brick):** Inside the `BrickPool`, an occupancy mask defines the solid status of a 4x4x4 block of voxels using 64-bit integers (`ulong`).
4. **Level 4 (Data Buffer / Voxel):** The actual material IDs (`uchar` / `uint8_t`) for the 1x1x1 voxels. 512 bytes per brick.
5. **Character Buffer:** Contains `CharacterGPUData` holding inverse model matrices (`simd_float4x4`) for up to 16 characters (1 bounding box + 6 body parts each). It dynamically streams CPU-animated character transforms to the GPU per frame. Note: strict 16-byte MSL alignment matching C++ `simd_float4x4` arrays is critical for correct data mapping.

**Toroidal Streaming:** `MaterialMap::UpdateStreaming(cameraPos)` fires every frame. As the player moves across sector boundaries, old sectors at the trailing edge of the 3D texture are unloaded, and new sectors at the leading edge are queued for async GPU procedural generation (`psoAnalyze`, `psoFill`).

## 4. The Rendering Pipeline (Deep Dive)
The `MetalRenderer::Draw()` loop executes an 8-Pass Deferred Compute Pipeline on the GPU.

1. **Pass 0: DistApprox (`distApproximationKernel`)**
   - Renders a half-resolution depth map. Optimizes ray starting points for the main passes.
2. **Pass 1: GBuffer & Direct Light (`GBufferAndDirectLight`)**
   - Full resolution. Shoots primary rays (`hitInfo = trace()`).
   - Computes Water logic (surface noise, reflections, specularity, refractions).
   - Trace shadow rays to the sun. Outputs Albedo, Normal, Motion Vectors, and Direct Lighting.
3. **Pass 2: Indirect Bounce (`IndirectBounce`)**
   - Hemisphere sampling via cosine-weighted random rays based on the `normal`.
   - Bounces rays to calculate Global Illumination (GI). Traces short shadow rays for the bounced light.
   - Output is extremely noisy.
4. **Pass 3: Temporal Accumulation (`TemporalAccumulation`)**
   - Uses Motion Vectors from Pass 1 to reproject the previous frame's Indirect Light.
   - Exponential moving average of the raw indirect light to settle the noise over time.
5. **Pass 4: Denoise (`BilateralDenoise`)**
   - An *A-Trous Edge-Avoiding Spatial Filter* executing in 3 iterations (Step widths: 1, 2, and 4).
   - Preserves geometry edges using Normal and Depth strictness weights while smoothing out the accumulated GI noise.
6. **Pass 5: Volumetric (`VolumetricFog`)**
   - Half-resolution raymarching through the SVO.
   - Samples shadow maps incrementally to compute realistic god-rays and scattering in empty air.
7. **Pass 6: Exposure (`ComputeExposure`)**
   - A compute shader that averages scene luminance and writes to a shared 1-element buffer to smoothly adapt camera exposure over time.
8. **Pass 7: Composite (`Composite`)**
   - Combines Direct Light, Denoised Indirect Light, Albedo, Volumetrics, and Skybox into an HDR buffer, applying the Exposure modifier and tone-mapping.
9. **Pass 8: TextOverlay (`TextOverlay`)**
   - Renders SDF (Signed Distance Field) text onto the composited image before upscaling.
   - Uses tile-culled rendering: the screen is divided into 64x64 pixel tiles. CPU builds a per-tile glyph list each frame. GPU pixels only iterate over glyphs in their tile (typically 1-5), not all 200+.
   - Each glyph is a screen-space quad. The SDF atlas is sampled for smooth, resolution-independent text.
   - Supports depth-tested 3D text (player name tags) and screen-space text (chat, HUD).
10. **Post-Process:** Apple `MetalFX` (Temporal Scaler/TAA) upscales to native resolution and provides anti-aliasing.

## 5. Raytracing Algorithms (`intersections.h`)
The heart of the performance lies in `intersections.h` (included by `.metal` kernels).
- **Character AABB Intersections:** Before voxel traversal, rays evaluate O(1) intersections against `CharacterGPUData` bounding boxes and 6 local body part AABBs (`[-0.5, 0.5]^3`). Ray collisions return Grass (`matID = 255`) and resolve local face normals accurately via inverse-transpose mapping. Primary rays skip self-intersections inside the player bounding box.
- **`GetStepPos()`**: Evaluates the hierarchy. Checks Level 1 (Indirection), then Level 2 (Sector Mask), then Level 3 (Occupancy). 
- **LOD Optimization:** If a region is empty or far away, it identifies the sparse bounds using `GetIsotropicLOD()` and skips vast empty spaces instantly by advancing the ray position to the cell boundary.
- **Bitwise Magic:** Utilizes `popcnt64()` and bitmasking (`BitTestHalf64`) against a `RayMaskOptimizationLUT` to cheaply calculate intersection boundaries within an 8x8x8 or 4x4x4 cell without standard AABB testing.

## 6. Text Rendering System

The engine uses a GPU compute-based SDF (Signed Distance Field) text rendering system that integrates cleanly into the existing compute pipeline without requiring a rasterization stage.

### Architecture
- **FontAtlas** (`FontAtlas.hpp/.cpp`): Generates SDF font atlas on CPU at startup using `stb_truetype.h`. Produces a 512x256 R8 texture with proper distance fields for all printable ASCII characters. Stores per-glyph metrics (UV coordinates, advance, bearing).
- **TextRenderer** (`TextRenderer.hpp/.mm`): Manages text layout, tile coverage, and GPU buffer updates. Each frame:
  1. `BeginFrame()` clears glyph list
  2. `AddText(text, x, y, scale, color)` lays out characters using font metrics, supports world-space projection for player names
  3. `EndFrame()` builds tile coverage: divides screen into 64x64 tiles, assigns each glyph to overlapping tiles
  4. `UpdateBuffers()` uploads glyph instances and tile data to GPU
- **text_overlay.shader**: GPU compute kernel (Pass 8). Each pixel:
  1. Looks up which tile it belongs to (O(1))
  2. Reads the tile's glyph list (typically 1-5 entries)
  3. For each glyph, checks AABB, samples SDF atlas, alpha-blends onto composite

### Key Design Decisions
- **Tile-culled rendering**: Instead of O(pixels × glyphs), each pixel only checks glyphs in its tile. With 200 glyphs spread across 510 tiles, average glyphs-per-tile is ~2-3. Total GPU work is negligible.
- **SDF over bitmap**: SDF provides resolution-independent, crisp text at any scale. The SDF atlas is 32KB (R8, 512x256) vs a bitmap atlas which would need multiple sizes.
- **Runs before MetalFX upscale**: Text is composited at render resolution, then upscaled with the rest of the scene. This ensures text benefits from TAA and upscaling.
- **Cross-platform**: Uses only compute shaders, no rasterization. Works identically on Metal, CUDA, and future WebGL backends.

### Adding Text in Code
```cpp
// In MetalRenderer::Draw(), before pipeline execution:
if (_fontAtlas.IsValid()) {
    _textRenderer.BeginFrame(State::dispWIDTH, State::dispHEIGHT);
    
    // Screen-space text (chat, HUD)
    _textRenderer.AddText("Hello World", 20.0f, 20.0f, 1.0f,
                          simd_make_float4(1,1,1,1), 0.005f);
    
    // World-space text (player names) - projected from 3D
    float4 clipPos = camera.viewProjection * float4(playerPos, 1.0f);
    float2 screenPos = (clipPos.xy / clipPos.w + 1.0f) * 0.5f * float2(width, height);
    _textRenderer.AddText(playerName, screenPos.x, screenPos.y, scale, color);
    
    _textRenderer.EndFrame();
    _textRenderer.UpdateBuffers(device);
}
```

## 7. Guidelines & Constraints for LLMs
1. **Never Break the GPU/CPU Boundary:** If you alter a struct in `ShaderTypes.h` (e.g., adding a float to `CameraData` or `FrameData`), be extremely mindful of alignment and padding (16-byte boundaries) since Metal and C++ must interpret the raw bytes identically. This applies to `GlyphInstance` and `TextOverlayData` as well.
3. **Performance is King:** Because path tracing is inherently slow, if you suggest a feature (e.g., glass refraction), implement it as cheaply as possible (single extra trace) rather than exploding the ray count.
4. **Text Rendering:** The text system uses tile-culled SDF rendering. When adding text features, use `TextRenderer::AddText()`. For world-space text (player names), project 3D positions to screen space using the camera's view-projection matrix before calling AddText.

## 9. Build System Notes

The project uses CMake with platform-specific configuration:
- **macOS**: Metal shaders compiled at build time, Objective-C++ sources
- **Windows**: CUDA kernels preprocessed from .shader files, compiled with nvcc

Key files in `CMakeLists.txt`:
- `src/renderer/Metal/` sources for macOS builds
- `src/renderer/CUDA/` and `src/renderer/D3D12/` sources for Windows builds
- `src/renderer/FontAtlas.cpp` and `src/renderer/TextRenderer.mm` for text rendering

Whenever implementing new features, refer to the pipeline map. E.g., adding localized light sources requires changes to Pass 1 (Direct) and Pass 2 (Indirect). Adding fluid physics requires touching `MaterialMap.mm` and `kernels/material_gen_kernel.metal`. Adding text or HUD elements uses the `TextRenderer` system described in Section 6.
